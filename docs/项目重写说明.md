## 一、项目定位

**这是一个本地单用户 AI Agent 工作台**，部署在个人电脑上，通过公司 OIDC 登录，核心用途：

- 与 LLM 对话，LLM 可调用工具（文件操作、网络请求、MCP 服务）
- 通过 MCP 协议连接公司内部服务（Jira、GitHub Enterprise）
- 定时生成工作日报、周报
- 将命令/查询结果可视化为图表页面，内嵌展示在当前界面

**不是**多用户 SaaS，**不是**云部署服务，**不需要**考虑水平扩展。

## 三、认证方案

**唯一登录方式：公司 OIDC**，不支持密码登录。

```
用户访问 / → 未登录 → 重定向到公司 IDP
    ↓ 用户在 IDP 完成登录
回调 /auth/oidc/callback，完成 PKCE 流程，换取 id_token
    ↓
验签 + 提取 claims（sub, email, name）
    ↓
写 session cookie（httponly, secure）作为会话凭证
```

**关键决策**：
- 不建 users 表（claims 即身份），或只建极简 preferences 表存用户设置
- PKCE state 存进程内 `map[string]PKCEState`，用 `time.AfterFunc` 做 10 分钟 TTL 清理（本地单实例安全）
- 无 JWT 黑名单：logout 只清 cookie，session 自然过期

## 五、核心架构：Agent Loop

这是整个系统最核心的部分，描述 orchestrator 每一轮的执行逻辑。

### 5.1 主循环结构

```
start_loop():
    构建静态 system prompt（只做一次）
    收集所有 MCP 工具（只做一次）
    进入 while 循环:
        步骤 1：检查是否被中止
        步骤 2：消费子 Agent 完成事件（注入摘要到消息历史）
        步骤 3：重算动态 system prompt（每轮）
        步骤 4：调用 LLM API（流式）
        步骤 5：处理 LLM 响应
            - end_turn：检查是否有未完成子 Agent → 等待或结束
            - tool_use：执行工具调用
        步骤 6：必要时压缩上下文
```

### 5.2 System Prompt 六层结构

System prompt 分为**静态层**（loop 开始时构建一次）和**动态层**（每轮重算）：

```
静态层：
  层 1 — 核心指令（orchestrator 角色定义，从 .md 文件读取）
  层 2 — 工具列表（走 SDK tools 参数，不写入 prompt）
  层 3 — Skill 元数据（只有名称和描述，不含内容正文）
  层 4 — 项目级指令（AGENTHUB.md，从项目根目录读取）

[分隔符]

动态层（每轮重算）：
  层 5 — 长期记忆索引（MEMORY.md 的一行摘要列表）
  层 6 — 动态上下文（最近消息摘要 + 可用 Agent 列表 + 当前任务图状态）
```

**为什么分两层**：静态层内容在一轮对话内不变，每轮重算是浪费。动态层包含任务状态，随子 Agent 完成而变化，必须每轮更新。

**层 3 Progressive Disclosure**：orchestrator 的 prompt 只注入 skill 名称和描述，不注入内容正文。LLM 需要时调用 `load_skill` 工具按需加载，避免 prompt 过长。

**层 6 注意**：查询任务图状态时必须绕过 ORM 的 identity map 缓存，直接从 DB 读取最新状态，否则会看到过期的任务状态。

### 5.3 关键执行顺序约束

**约束 A（最重要）**：工具调用时，必须先执行所有 PRE_TOOL_USE hook 拿到最终入参，再将工具调用记录写入消息历史，最后才执行工具。

```
✓ 正确顺序：fire PRE_TOOL_USE → 写消息历史 → 执行工具
✗ 错误顺序：写消息历史 → fire PRE_TOOL_USE → 执行工具
```

原因：如果 hook 修改了工具入参（如审批改写路径），而消息历史里记录的是原始入参，LLM 下一轮会看到不一致，产生幻觉。

**约束 B**：子 Thread 的状态必须在任何延迟（如计划延迟启动）之前标记为"运行中"。

原因：如果先延迟再标记，调度器在延迟期间会误判无活跃任务，提前触发"本轮完成"信号。

**约束 C**：取消会话内所有 Thread 时，每个 Thread 必须用独立的短数据库事务，不能共用一个长事务。

原因：orchestrator 的 finally 块持有某些行的锁，长事务会触发锁等待超时。

### 5.4 子 Agent 消息 ID

子 Agent 回复消息的 ID 必须独立生成，不能复用触发该 Thread 的用户消息 ID。

原因：前端用消息 ID 作为 map 的 key，复用会导致两条消息互相覆盖。

## 六、MCP 工具路由

### 6.1 工具收集

loop 启动时，枚举所有已挂载 MCP 服务器的工具列表，建立 `toolName → MCPClient` 路由表。内置工具（文件操作、deploy 等）单独注册。

```
工具调用路由逻辑：
  if toolName in mcp_tool_client_map:
      → 转发给对应 MCPClient 执行
  else:
      → 走内置工具 registry 执行
```

### 6.2 两个内网 GitHub 实例

需同时挂载：
- `github.tools.sap`（org: hci, common-service-infrastructure）
- `github.wdf.sap.corp`（org: DBaaS, hanadatalake, delphi）

注意：两个实例的工具名可能相同（如都有 `search_commits`），挂载时需加实例前缀避免冲突。

### 6.3 MCP OAuth Token 管理

部分 MCP 服务器需要 OAuth token（如公司内部 API）：
- 优先从 DB 取缓存 token（提前 30 秒判过期）
- Client Credentials 模式：自动用 client_id/secret 换新 token 存 DB
- OIDC 模式：需用户重新授权，返回授权 URL

## 七、Hook 系统

### 7.1 结构

```
PRE_TOOL_USE 同步 hook 链（串行执行，可中止工具调用）：
  → SecurityHook（路径穿越检查、黑名单工具）
  → ApprovalHook（高危工具触发人工审批）

POST_TOOL_USE 异步 hook（goroutine，不影响主流程）：
  → AuditHook（记录工具调用日志）
```

**同步 hook**：串行执行，任一返回 block 则抛异常中止工具调用，可修改工具入参（后续 hook 看到修改后的值）。

**异步 hook**：用 `go func()` + 深拷贝 context 执行，纯观察，不影响决策。

### 7.2 审批机制

高危工具（`create_file`、`edit_file`、`deploy_app`）触发人工审批：

```
1. 生成 approval block_id
2. 写 DB（状态: pending）
3. 推 SSE 事件给前端（显示审批气泡）
4. 注册 pending approval（Go channel）
5. 等待用户决定（超时 120 秒视为拒绝）
```

**审批决定处理（顺序不可颠倒）**：
```
✓ 正确：先写 DB（approved/rejected）→ 再 signal channel
✗ 错误：先 signal channel → 再写 DB
```
原因：颠倒后，主循环立即恢复，用户刷新页面会看到 DB 中仍是 pending 状态。

**清理**：无论审批通过/拒绝/超时，finally 块必须从 pending map 中删除该 block_id，防止内存泄漏。

**批量审批**：同一轮有 ≥2 个文件写操作时，合并为一次审批请求，用户一次性决定。批量通过后，后续单个文件操作直接放行（通过 context 中的 flag 传递）。

**审批落库失败处理**：新项目改为 fail-closed——落库失败时不放行，直接拒绝执行，并向用户报告。（旧项目是 fail-open，是已知安全问题。）

### 7.3 审计日志

只记录工具调用的入参 key 名称，不记录 value。

原因：value 可能包含文件内容、API key 等敏感信息。

## 九、子 Agent 执行

### 9.1 运行时 Header 注入

每个子 Agent 执行时，在其 system prompt 最前面注入运行环境 header，内容包括：
- Agent 自己的 ID、名称、描述
- 是否有 MCP 工具权限
  - 有（anthropic_sdk/custom 类型）：说明可用工具列表
  - 无（其他类型）：明确告知"所有真实操作由 orchestrator 执行，你只输出文本"
- 沙箱路径：`sandbox/{conversation_id}/`
- 协作规则

**核心安全约束**：子 Agent 没有工具调用权限。所有高危操作（写文件、部署、调 MCP）只能由 orchestrator 执行。这是审批门控能够生效的前提。

### 9.2 Skill 注入

- orchestrator 的 prompt 只注入 skill 名称/描述（Progressive Disclosure）
- 子 Agent 执行时注入完整 skill 内容（内置 skill 从 `.md` 文件读取，DB 存元数据）
- `.md` 文件是内置 skill 的唯一真相源，启动时幂等同步到 DB

## 十、SSE 流式输出协议

前端通过 SSE 接收 Agent 输出，事件类型：

| 事件 | 说明 |
|---|---|
| `agent_start` | 开始输出，前端创建流式气泡 |
| `block_start` | 新 Block 开始（文本/工具调用/审批等），携带 block_id |
| `block_delta` | Block 增量内容，逐 token 追加 |
| `block_stop` | Block 完成，携带最终数据 |
| `message_appended` | 独立新消息（diff 展示、审批气泡等）|
| `approval_requested` | 审批请求 |
| `thread_status` | 子 Thread 状态变更 |
| `round_done` | 本轮完成，前端清理 streaming 状态 |
| `queue_drained` | 队列清空，前端断开 SSE |

**关键**：`round_done` 和 `queue_drained` 是信号性事件，必须保证送达（队列满时清空再推，不能丢弃）。丢失会导致前端一直显示"思考中"。

**审批气泡和 diff 展示**必须用 `message_appended` 事件（作为独立消息推送），不能用 `block_start`（否则会被塞进当前 streaming 气泡里）。

## 十一、功能清单与实现阶梯

### MVP（阶段 0-3）：登录 + 对话 + MCP + 自动日报

**阶段 0：基础骨架**（前置）
- Go HTTP server + OIDC 登录（PKCE flow）
- Anthropic SDK 集成，基础流式对话
- MySQL + DB 迁移，messages/conversations 表
- 前端套模板，对话 UI + SSE 接收

**阶段 1：Agent 工具能力**（低难度）
- Tool Registry（`init()` 注册）
- Hook 骨架（同步串行 + 异步 goroutine）
- 基础工具：`read_file`、`list_directory`、`fetch_url`、`respond_to_user`
- System Prompt 六层管道（静态层一次构建，动态层每轮重算）

**阶段 2：MCP 接入**（中难度）
- MCPClient 实现（支持 stdio/SSE/HTTP 三种传输）
- loop 启动时枚举工具，建路由表
- 挂载 GitHub MCP（`github.tools.sap` + `github.wdf.sap.corp`）
- 挂载 Jira MCP

**阶段 3：定时任务**（中难度，依赖阶段 2）
- **GitHub 日报**：每天 09:00，查两个 GitHub 实例前一天人工 commits/merged PR，过滤 bot（login 含 `serviceuser` 或 `[bot]` 的跳过），按仓库分组，存入固定"日报"会话，前端置顶
- **周报草稿**：每周五 17:00，汇总本周自己的 commits + 关闭 Jira issue，生成可复制文本
- **Sprint 看板**：启动时拉取当前 Sprint 分配给自己的 issue + 对应 PR 状态

## 十二、数据库 Schema 要点

仅列出与核心逻辑相关的约束，具体字段自行设计：

- `messages.content`：JSON 数组，存有序的 ContentBlock（text/tool_use/approval/code 等类型）
- `threads.blocked_by`：JSON 数组，存依赖的 thread_id 列表，全部完成后才解锁
- `threads.agent_id = 'orchestrator'`：标识主 Agent thread，其余为子 thread
- `mcp_tokens`：唯一约束 `(user_id, server_id)`，存 OAuth token + expires_at
- 消息分页：用 `(created_at, id)` 复合游标，防止同毫秒消息丢失；游标 `id` 必须校验属于当前会话

## 十三、安全边界

- 所有文件操作工具必须在执行前将路径 `resolve()` 后检查是否在 `sandbox/{conversation_id}/` 内，越界直接拒绝（不依赖上层 hook，handler 层自己校验）
- 子 Agent 无工具权限（见第九节）
- 审批落库失败 fail-closed（见第七节）
- 工具调用日志只记录 key，不记录 value（见第七节）
